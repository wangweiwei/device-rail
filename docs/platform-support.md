# Platform support and setup boundaries

DeviceRail exposes platform implementations through one Driver contract, but
it does not hide or download external platform automation services. A Driver's
presence in the repository means it passes the shared conformance contract; it
does not imply every device, OS version, permission combination, or vendor tool
has been tested.

## Android

- Requires an operator-installed `adb`.
- Enable with `DEVICERAIL_ANDROID=auto|required`; use `off` to disable it.
- DeviceRail never bundles Android Platform Tools.
- Setup and action details: [Android Driver](../crates/android-adb/README.md).

## iOS and iPadOS

- Direct WDA remains the compatibility default. External mode accepts an
  operator-built/running WebDriverAgent endpoint via
  `DEVICERAIL_IOS_WDA_ENDPOINT` plus `DEVICERAIL_IOS_DEVICE_TOKEN`; optional
  MJPEG remains operator-managed.
- Select the Appium XCUITest backend with
  `DEVICERAIL_IOS_BACKEND=appium`, then choose exactly one server mode: a
  bounded numeric-loopback HTTP endpoint in `DEVICERAIL_IOS_APPIUM_ENDPOINT`,
  or an operator-selected executable in `DEVICERAIL_IOS_APPIUM_PATH`.
  `direct-wda` is the only other accepted backend value. Appium and Direct WDA
  cannot be enabled together for one route.
- `DEVICERAIL_IOS_SESSION_TARGET=native|safari` selects the initial XCUITest
  Session target and defaults to `native`. `safari` is supported only by the
  Appium backend and is rejected for Direct WDA.
- `DEVICERAIL_IOS_APPIUM_NEW_COMMAND_TIMEOUT_SECONDS` sets the typed
  `appium:newCommandTimeout` capability. The default is `600` seconds and the
  accepted range is `1..=3600`; malformed, zero, or out-of-range values fail
  startup, and the setting is rejected for Direct WDA. Explicitly expired
  Sessions are replaced before the next operation without replaying ambiguous
  mutations.
- DeviceRail never downloads Appium, XCUITest Driver, Node.js, or platform
  packages. External endpoint mode leaves process ownership with the operator.
  Executable mode starts Appium with fixed numeric-loopback address, port, and
  base-path arguments, waits for bounded readiness, detects an early exit, and
  terminates the owned child during daemon shutdown. Optional
  `DEVICERAIL_IOS_APPIUM_PORT` defaults to `0` (an available port) and
  `DEVICERAIL_IOS_APPIUM_BASE_PATH` defaults to `/`; they are invalid without
  `DEVICERAIL_IOS_APPIUM_PATH`. DeviceRail creates and deletes the W3C Session
  when its iOS Driver connects and disconnects.
- The stock daemon's Appium capabilities are closed and generated by
  DeviceRail. The daemon
  injects XCUITest, UDID, device name, platform version, Safari WebView
  discovery, and an optional validated WDA endpoint. Without an explicit WDA
  endpoint, it omits `appium:webDriverAgentUrl` so XCUITest Driver manages the
  bundled `appium-webdriveragent` for a physical device or Simulator. It does
  not accept arbitrary capability JSON or credentials from environment
  variables.
- Managed macOS mode uses `DEVICERAIL_IOS=auto|required` and an explicit
  `DEVICERAIL_IOS_WDA_PROJECT` for Direct WDA or an explicitly attached WDA.
  Discovery merges bounded `devicectl` physical-device inventory (with
  `xcdevice` fallback) and `simctl` Simulator inventory. Only an available
  `Booted` Simulator is connected. An explicit `DEVICERAIL_IOS_DEVICE_TOKEN`
  may select either kind. Without one, the unique connected physical device is
  preferred; only when no physical device is connected is the unique booted
  Simulator selected. Multiple eligible targets require an explicit UDID.
  DeviceRail does not create or boot Simulators.
- Host-managed Direct/attached WDA reuses a fingerprinted DerivedData build,
  starts `xcodebuild test-without-building`, waits for WDA, and supervises
  recovery. A physical target additionally requires signing, trust, Developer
  Mode, developer services, and numeric-loopback `iproxy`. A Simulator skips
  those physical-device requirements and makes WDA listen directly on the
  selected host-local port. Appium without a WDA project leaves WDA
  build/start/recovery to XCUITest Driver for either target kind.
- In `auto`, a later physical-device connection or operator-initiated Simulator
  boot can publish a route without restarting the daemon. A published route
  keeps its original UDID while unavailable and never adopts another target.
  Host-managed Direct/attached WDA revalidates and relaunches its owned
  processes when that target returns. In bundled-WDA Appium mode, XCUITest
  Driver owns WDA creation/recovery when a W3C Session is created again.
- Run `devicerail-daemon ios doctor` (or the source-workspace
  `devicerail-ios doctor`) before managed startup for structured tool,
  signing, CoreDevice, pairing, Developer Mode, developer-service, and WDA
  diagnostics. When `DEVICERAIL_IOS_BACKEND=appium`, the daemon doctor either
  probes the external `/status` endpoint or temporarily launches and probes
  the selected executable, then reports fixed, redacted remediation if Appium
  is unavailable or not ready. `/status` alone does not prove the XCUITest
  extension is installed; install it explicitly with
  `appium driver install xcuitest`. A missing or incompatible extension is
  surfaced as an explicit Session-creation error on `device.connect`.
- DeviceRail never stores Apple credentials or bypasses physical-device trust,
  Developer Mode/restart, UI Automation, or developer-certificate trust. These
  physical-device gates are not required for a Simulator.
- Protocol 1.5 defines a provider-neutral UI Snapshot, selector, node-reference,
  and semantic-Action contract. The Appium backend implements the five
  canonical Actions through native accessibility and Safari/WebView DOM
  channels. Direct WDA remains the native coordinate/key compatibility backend
  and does not advertise those element Actions. Protocol support alone is not
  a claim that an arbitrary Driver exposes native or web element control.
- One device may have only one WebDriver Session owner. Direct WDA is the
  native-only compatibility backend; the Appium XCUITest backend owns both
  native and Safari/WebView contexts while reusing the same external or
  Host-managed WDA endpoint when one is explicitly supplied. Otherwise it
  uses XCUITest Driver's bundled WDA. Backend selection occurs before Driver
  registration, so the stock daemon constructs only one Session owner for the
  route.
- Setup and action details: [iOS Driver](../crates/ios-webdriver/README.md).
- Managed lifecycle details: [iOS Host](../crates/ios-host/README.md).

## HarmonyOS

- Requires an operator-installed `hdc`.
- Enable with `DEVICERAIL_HARMONY=auto|required`; the default is `off`.
- DeviceRail does not download DevEco Studio, an SDK, or device packages.
- Setup and action details: [HarmonyOS Driver](../crates/harmony-hdc/README.md).

## Native desktop

- Enable with `DEVICERAIL_DESKTOP=auto|required`; the default is `off`.
- macOS requires Screen Recording and Accessibility permission.
- Windows requires an interactive desktop session.
- Linux requires explicit X11 or Wayland capture/input tools and configuration.
- Setup and capability details: [Desktop Driver](../crates/desktop-driver/README.md).

## Playwright

- Requires an already-running, version-compatible Playwright server.
- DeviceRail uses `playwright-core`; it does not download or launch browsers.
- The stock helper supports the public `browserType.launchServer()` endpoint,
  keeps one connection alive, and creates one blank context/page only when the
  server exposes none.
- `elementExists` and `textContains` provide bounded, machine-checkable page
  assertions without returning DOM or page text.
- `waitForSelector` waits for a closed element state; `clickByText` clicks the
  single visible text match (ambiguity fails closed); `readValueNearLabel`
  reads the value laid out next to a unique label by run-time geometry and
  returns a bounded `{ "value": string }`.
- Set `DEVICERAIL_PLAYWRIGHT_ENDPOINT` and, when necessary, the browser, Node,
  and helper settings documented in the [main README](../README.md#daemon-configuration).
- Bridge details: [Playwright Remote Driver](../packages/playwright-driver/README.md).

## RDP

- Requires an operator-managed bridge on numeric loopback.
- DeviceRail does not embed an RDP client stack or manage remote credentials.
- Set `DEVICERAIL_RDP_BRIDGE`, `DEVICERAIL_RDP_TARGET`, and
  `DEVICERAIL_RDP_TOKEN`.
- Bridge contract: [RDP Remote Driver](../crates/rdp-remote/README.md).

## Plugins and remote nodes

- Process plugins are opt-in and require owner-only files on supported Unix
  platforms: [Plugin ABI](../crates/plugin-driver/README.md).
- Distributed routes require operator-managed SSH/mTLS tunnels terminating on
  loopback: [Distributed router](../crates/distributed-router/README.md).
- RPC HMAC authentication does not replace TLS or automatically authenticate
  the peer protocol: [Remote authentication](../crates/remote-auth/README.md).

## Reading validation claims

- **Conformance** means the Driver passed the shared deterministic contract.
- **Daemon E2E** means a stock daemon exercised the integration boundary,
  sometimes with controlled fake platform tools.
- **Real-device validated** means the specific path was exercised on actual
  hardware and host software; it is not a compatibility guarantee for all
  versions.
- **External release validation** includes real multi-OS labs, certificates,
  Apple notarization, remote networks, and production signing keys.

The exact implemented and externally pending scope is maintained in
[ROADMAP.md](../ROADMAP.md).
